# State-preserving operational checks

Use the exact archived raw genesis specification for check-block, export-blocks, export-state, import-blocks and revert. These commands now reconstruct its genesis hash in memory, preserving its `:code`, child state and Wasm state version, and compare it with the database genesis before running the requested operation. A newly built `--dev` specification is not a substitute for an existing database's genesis. This local correction has not been installed in production.

On disposable database copies, all five commands refused the wrong genesis; correct-genesis checking succeeded; resuming an interrupted binary import reproduced all188 retained block81 top-state entries; a normal large revert stopped at finalized block1 and preserved the genesis/finality hashes. This does not authorize production reverts or claim that finalized runtime upgrades can be rolled back by replacing a binary.

`era-node upgrade-check --snapshot PUBLIC_FINALIZED_JSON --wasm REVIEWED_COMPRESSED_WASM --genesis EXPECTED_GENESIS` is an offline diagnostic. It opens no network or node database, reads no keys and creates no transaction. It checks the header hash and complete top-state root, rejects unsupported child tries, requires source spec14 and candidate spec15/transaction1 identity, then executes first-block initialization in the actual Wasm. An old-runtime execution of the same synthetic header distinguishes normal block bookkeeping from upgrade changes. Protected balances, vesting, custody, issuance/reward/application/authority records must match; only Staking ordinary author reward-point changes are permitted relative to the initial snapshot and must exactly match the old-runtime control. This is not full production block execution or deployment approval. Fresh capture and full release checks remain required.

`era-node offline-scenario --input SCENARIO_JSON --output NEW_EVIDENCE_DIRECTORY` executes a bounded synthetic signed Wasm scenario. It allows only fixed public `RelaunchCommunity` and `RelaunchSudo` development identities, creates a distinct synthetic genesis and refuses an existing output directory. Up to16000 blocks/64 calls and optional bounded monotonic timestamps support exact off-chain service deadlines without wall-clock waiting. Synthetic BABE headers do not establish independent consensus finality, actual weather results or deployed operator independence. Use the four-validator network evidence for real consensus/finalized transaction behavior.

## Continuous receipt binding during an approved binary adoption

The retained fleet supervisor verifies the entire installed release manifest, a separate root-owned deployment authority, and the receipt/continuous-acceptance hashes. Replacing only the binary invalidates these bindings. `tools/v14-release/prepare_continuous_rebind.py` prepares public-record proposals, never installs them. It verifies the existing hash chain and preserves original commissioning start/deadline, accepted epoch, policy, mode, high-water/usage values and storage pauses. Only manifest/receipt/acceptance references change. Focused positive and tamper/host/startup/renewal tests pass. At authorized execution, stop only the selected supervisor, preserve its live records, compute and review the bound replacements, update deployment authority for that exact release, and install the three records before restarting. Recover a failed local file-install step from its preserved originals while the service remains stopped. This is not a reset of the completed observation or permission to overwrite history.


The retained production supervisor hard-codes spec14. This transition guard is not independent fleet monitoring and its in-memory version floor does not persist across supervisor restarts; final acceptance separately requires spec15 on every node.
